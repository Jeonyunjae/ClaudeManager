# 기능 목록
> 작성: planner | 상태: v2.0 — 수용 기준(AC) 추가

## A. Skill 엔진

### F001. Skill 실행 엔진 — P0
> schema/execute 두 가지 모드로 Skill을 실행하는 핵심 엔진

**트리거**: 사용자가 UI에서 Skill을 선택하고 실행 버튼 클릭
**수용 기준**:
- [ ] `POST /api/skills/:name/schema` 호출 시 bash Skill을 `schema` 모드로 실행하여 JSON 스키마를 반환한다
- [ ] `POST /api/skills/:name/execute` 호출 시 bash Skill을 `execute` 모드로 실행한다
- [ ] bash Skill 실행은 `child_process.execFile`로 실제 `.sh` 파일을 실행한다 (DB INSERT만이 아님)
- [ ] Skill 실행 결과로 Part 폴더(`.orchestrator/parts/<name>/`)를 생성한다
- [ ] Skill 실행 결과로 Hooks 설정 파일(`.claude/hooks.json`)을 생성한다
- [ ] Skill 실행 결과로 승인 정책 파일을 생성한다
- [ ] 실행 성공/실패를 DB에 기록하고 WebSocket으로 브로드캐스트한다
- [ ] 실행 실패 시 에러 메시지와 스택 트레이스를 DB에 저장한다
**검증**: Skill 실행 후 파일시스템에 폴더/파일이 생성되고, DB 레코드가 존재하며, bash 프로세스가 실행된 로그가 남는다

---

### F002. 기본 Skill 제공 — P0
> `base-part.sh`(부모)와 `project-part.sh`(자식) 기본 제공

**트리거**: 프로젝트 초기 설치 시
**수용 기준**:
- [ ] `~/.claudemanager/skills/base-part.sh` 파일이 존재한다
- [ ] `~/.claudemanager/skills/project-part.sh` 파일이 존재한다
- [ ] `base-part.sh`는 `schema` 모드에서 공통 필드(name, description, sensitivity_level)를 포함하는 JSON을 출력한다
- [ ] `project-part.sh`는 `source base-part.sh`로 부모를 로드하고 프로젝트 전용 필드를 추가한다
- [ ] 두 Skill 모두 `execute` 모드에서 .orchestrator/ 폴더 구조를 생성한다
**검증**: `bash base-part.sh schema`, `bash project-part.sh execute '{"name":"test"}'`를 직접 실행하여 결과 확인

---

### F003. 단일 상속 메커니즘 — P0
> `source` 기반으로 부모 Skill을 로드하는 상속 구조

**트리거**: 자식 Skill이 실행될 때
**수용 기준**:
- [ ] 자식 Skill 내부에서 `source $SKILL_DIR/base-part.sh`로 부모 함수/변수를 로드한다
- [ ] 부모 스키마 필드 + 자식 스키마 필드가 합쳐져 반환된다
- [ ] 부모의 execute 로직 실행 후 자식의 추가 로직이 실행된다
**검증**: 자식 Skill의 schema에 부모 필드가 포함되는지, execute에서 부모 로직이 먼저 실행되는지 확인

### F004. Skill 라이브러리 관리 — P0
> `~/.claudemanager/skills/`에서 Skill 등록, 조회, 삭제

**트리거**: 사용자가 설정 > Skill 관리 메뉴 접근
**수용 기준**:
- [ ] `GET /api/skills` 호출 시 `~/.claudemanager/skills/` 디렉토리를 스캔하여 `.sh` 파일 목록을 반환한다
- [ ] 파일시스템의 Skill 파일과 DB의 skills 테이블이 동기화된다
- [ ] 새 Skill 파일 등록(업로드/생성) 시 파일시스템에 저장한다
- [ ] Skill 삭제 시 파일시스템에서 제거하고 DB에서도 삭제한다
- [ ] UI에서 Skill 라이브러리 목록이 표시되고 각 Skill의 이름, 버전, 설명이 보인다
**검증**: 파일시스템에 `.sh` 파일을 추가/삭제한 후 API 응답에 반영되는지 확인

### F005. 스키마 기반 입력 폼 — P0

**트리거**: 사용자가 Skill을 선택하여 실행하려 할 때
**수용 기준**:
- [ ] Skill의 `schema` 모드 실행 결과 JSON을 파싱한다
- [ ] JSON의 fields 배열을 기반으로 text/select/number 타입 입력 폼을 자동 생성한다
- [ ] required 필드에 대한 유효성 검증이 동작한다
- [ ] 폼 제출 시 입력값을 `execute` 모드로 전달한다
- [ ] SkillFormModal 컴포넌트가 동적으로 렌더링된다
**검증**: 다양한 필드 타입을 가진 Skill 스키마로 UI가 올바르게 생성되는지 확인

**수용 기준**:

- [ ] Skill 실행 시 `.orchestrator/parts/<name>/input.json` 파일을 생성한다 (입력값 기록)
- [ ] DB의 parts 테이블에 skillVersion, inputJson 필드가 저장된다
- [ ] 동일 입력으로 Skill을 재실행하면 동일한 결과가 나온다
**검증**: Skill 실행 후 lock 파일과 input.json이 생성되고, 내용이 정확한지 확인

## B. 4계층 오케스트레이션

### F008. Main 오케스트레이터 관리 — P0
> 최상위 오케스트레이터 시작, 상태 관리, 지시 전달

**트리거**: 시스템 시작 시 / 사용자가 Main 시작 명령
**수용 기준**:
- [ ] 시스템 시작 시 Main용 tmux 세션(`cm-main`)을 생성한다
- [ ] tmux 세션 내에서 `claude --dangerously-skip-permissions` 프로세스를 실행한다
- [ ] Main의 CLAUDE.md 파일을 `.orchestrator/main/CLAUDE.md`에서 로드한다
- [ ] Main의 상태(active/idle/error)를 DB에 기록하고 WebSocket으로 브로드캐스트한다
- [ ] 사용자 채팅 메시지를 Main의 tmux 세션 stdin으로 전달한다
- [ ] Main의 stdout를 캡처하여 채팅 메시지로 반환한다
**검증**: `tmux ls`에서 cm-main 세션이 보이고, Claude Code 프로세스가 실행 중이며, 채팅이 양방향으로 동작하는지 확인

---

### F009. Part 동적 생성 — P0
> Skill 실행을 통한 Part 오케스트레이터 동적 생성

**트리거**: Skill execute 성공 시
**수용 기준**:
- [ ] Skill execute 결과로 Part 레코드를 DB에 생성한다
- [ ] `.orchestrator/parts/<name>/` 폴더를 생성한다 (main-context.md, sub-contexts/, decisions/, progress/)
- [ ] Part용 tmux 세션(`cm-part-<name>`)을 생성하고 Claude Code를 실행한다
- [ ] Hooks 설정(`.claude/hooks.json`)에 해당 Part의 이벤트 수신 설정을 추가한다
- [ ] 승인 정책 파일(`.orchestrator/parts/<name>/policy.json`)을 생성한다
- [ ] WebSocket으로 `part:created` 이벤트를 브로드캐스트한다
- [ ] UI 워크스페이스에 새 Part 영역이 표시된다
**검증**: Skill 실행 후 tmux 세션, 폴더 구조, Hooks 설정, DB 레코드가 모두 생성되는지 확인

---

### F010. Sub 오케스트레이터 관리 — P0
> Part 내 Sub 생성, 시작, 정지, 상태 관리

**트리거**: Part 오케스트레이터가 Sub를 생성할 때 / 사용자가 수동 생성
**수용 기준**:
- [ ] Sub용 tmux 세션(`cm-sub-<id>`)을 생성하고 Claude Code를 실행한다
- [ ] Sub의 CLAUDE.md를 `.orchestrator/parts/<part>/sub-contexts/<sub>/CLAUDE.md`에서 로드한다
- [ ] Sub 시작/정지/재시작 API가 실제로 tmux 세션을 제어한다 (kill-session, respawn)
- [ ] Sub 상태 변경 시 DB 업데이트 + WebSocket `agent:status` 브로드캐스트
- [ ] Sub 정지 시 현재 작업 상태를 context.md에 기록한다
**검증**: API 호출 후 `tmux ls`에서 세션이 생성/제거되고, DB 상태가 일치하는지 확인

---

### F011. 인스턴스 관리 — P0
> Sub의 태스크 외주를 위한 인스턴스 생성, LiteLLM 경유 모델 호출

**트리거**: Sub 오케스트레이터가 인스턴스 생성을 요청할 때
**수용 기준**:
- [ ] 인스턴스용 tmux 세션(`cm-inst-<id>`)을 생성한다
- [ ] 인스턴스의 모델은 LiteLLM(localhost:4000)을 경유하여 호출한다
- [ ] 인스턴스 완료/실패 시 Sub에게 결과를 전달한다
- [ ] 인스턴스 상태를 DB에 기록하고 WebSocket으로 브로드캐스트한다
- [ ] 동시 실행 인스턴스 수가 maxConcurrentAgents 설정값을 초과하지 않는다
**검증**: 인스턴스 생성 후 tmux 세션이 존재하고, LiteLLM 로그에 호출이 기록되는지 확인

---

### F012. 에이전트 트리 구조 — P0
> Main -> Part -> Sub -> 인스턴스 계층 구조 유지 및 조회

**트리거**: `GET /api/agents/tree` 호출 시
**수용 기준**:
- [ ] Main → Part → Sub → Instance 4계층 트리 JSON을 반환한다
- [ ] 각 노드에 id, name, role, status, children이 포함된다
- [ ] 실시간 상태(active/idle/pending/error/stopped/retrying)가 반영된다
- [ ] 에이전트 생성/삭제 시 트리가 즉시 업데이트된다
**검증**: 여러 계층의 에이전트가 존재할 때 트리 구조가 정확히 반환되는지 확인 ✅ 완전 구현

**검증**: 에이전트 상태를 변경했을 때 대시보드에 실시간 반영되는지 확인

### F015. 인스턴스 상세 뷰 — P0
> 실시간 터미널 화면(xterm.js) + stdin 입력 전송(양방향 제어), 작업 로그 표시

**트리거**: 에이전트 모달에서 터미널 탭 선택
**수용 기준**:
- [ ] xterm.js 터미널이 해당 에이전트의 tmux 세션에 연결된다
- [ ] 에이전트의 stdout가 실시간으로 터미널에 표시된다 (WebSocket `terminal:output`)
- [ ] 사용자가 터미널에 입력하면 에이전트의 stdin으로 전달된다 (WebSocket `terminal:input`)
- [ ] 터미널 크기 조정이 동작한다 (`terminal:resize`)
- [ ] 작업 로그 탭에서 에이전트의 이벤트 로그가 시간순으로 표시된다
**검증**: 터미널에서 명령어를 입력했을 때 에이전트의 tmux 세션에 반영되는지 확인

### F017. 시스템 헬스 모니터링 — P0
> CPU/메모리/디스크/네트워크 실시간 모니터링, 임계값 알림

**트리거**: 설정 > 시스템 헬스 패널 또는 대시보드 접근
**수용 기준**:
- [ ] CPU 사용률을 `os.cpus()`로 계산하여 퍼센트로 반환한다
- [ ] 메모리 사용률을 `os.freemem()/os.totalmem()`으로 계산한다
- [ ] 디스크 사용률을 `child_process.exec('df -k /')`로 계산한다 (하드코딩 0% 금지)
- [ ] 네트워크 사용량을 시스템 명령으로 수집한다 (하드코딩 0 금지)
- [ ] 헬스 데이터를 주기적으로 DB에 기록한다 (히스토리)
- [ ] 임계값 초과 시 알림을 생성한다
- [ ] WebSocket `system:health` 이벤트로 실시간 업데이트한다
**검증**: `/api/system/health` 응답에서 cpu, memory, disk, network가 모두 실제 값(0%가 아닌)인지 확인

- [ ] `terminal:connect`/`terminal:disconnect`로 연결을 관리한다

- [ ] SQLite DB 파일을 복사한다 (WAL 체크포인트 후)
- [ ] `.orchestrator/` 폴더를 압축 백업한다
- [ ] 백업 파일을 `$CLAUDEMANAGER_HOME/backups/`에 날짜별로 저장한다
- [ ] 오래된 백업은 보존 정책에 따라 자동 삭제한다
- [ ] 백업 상태를 DB에 기록한다
- [ ] 설정에서 백업 주기를 변경할 수 있다
**검증**: 스케줄러 동작 후 백업 파일이 생성되고, DB에 기록되는지 확인

## 수용 기준 작성 원칙

이 문서의 수용 기준은 다음 원칙을 따른다:

1. **구현 범위 명확화**: "DB INSERT만"이 아닌, 실제 프로세스 실행/파일 생성/이벤트 발행까지 포함
2. **검증 가능성**: 각 기준은 "예/아니오"로 판단 가능한 형태
3. **의존성 명시**: 다른 기능에 의존하는 경우 `(F0XX 의존)` 또는 `(F0XX 구현 시)`로 표기
4. **현재 구현 상태 표기**: 이미 완전 구현된 기능은 `✅ 완전 구현`으로 표기
