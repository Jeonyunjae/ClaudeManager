## 1. 핵심 도메인 개념

### 1.1 조직 계층 (4계층 아키텍처)

#### Main 오케스트레이터 (비서실장)
- 시스템의 최상위 오케스트레이터
- 대표의 지시를 받아 Part에 전달
- 전체 Part의 상태를 총괄 관리
- 반드시 Claude Code로 실행 (파일 시스템 접근, 도구 실행, Hooks 필수)

#### Part 오케스트레이터 (부서장)
- 특정 도메인(부서)을 담당하는 오케스트레이터
- **Skill을 통해서만 동적으로 생성** (하드코딩 금지)
- 도메인 내 복수 Sub를 관리
- 예: 프로젝트 Part가 여러 개발 프로젝트를 Sub 단위로 운영
- 반드시 Claude Code로 실행
- Part별 승인 정책, 재시도 정책, 민감도 수준을 독립 보유

#### Sub 오케스트레이터 (팀장)
- Part 내에서 개별 프로젝트/업무를 담당
- 인스턴스들을 관리하고 태스크를 분배
- Part 내 Sub 간 독립 운영 (간섭 없음)
- 반드시 Claude Code로 실행
- 의사결정이 필요하면 Main에게 전달 (대표에게 직접 요청 불가)

#### 인스턴스 (외부 전문 인력)
- Sub가 부분 태스크를 외주하는 용도 (리뷰, 분석, 요약 등)
- LiteLLM을 경유하여 다양한 AI 모델 사용 가능
- Claude Code가 아닌 일반 모델 호출 가능

### 1.2 Skill 시스템

#### Part Skill
- Part 생성을 위한 bash 스크립트
- 메타데이터 + 입력 스키마 + 실행 로직으로 구성
- **Skill : Part = 1 : 1** (같은 Skill로 여러 Part 생성 금지)
- Skill 라이브러리(`~/.claudemanager/skills/`)에 등록

#### 기본 Skill
- `base-part.sh`: 모든 Skill의 부모, 공통 로직 정의
- `project-part.sh`: MVP 기본 제공, 개발 프로젝트 Part 생성

#### 단일 상속
- `source` 명령으로 부모 Skill 로드
- 다중 상속 금지, 단일 상속만 허용
- 부모의 공통 로직을 자식이 확장/오버라이드

#### Skill 실행 모드
- **schema 모드**: 입력 스키마를 반환 (UI 폼 자동 생성용)
- **execute 모드**: 스키마 기반 입력을 받아 Part 실제 생성

#### Skill 버전 관리
- `skill-version.lock`: 실행 시점의 Skill 버전 기록
- `input.json`: 실행 시 입력된 기준 정보 기록
- 재현성 보장

### 1.3 의사결정 흐름 (Human-in-the-Loop)

#### 승인 요청
- Sub에서 발생한 의사결정 요구
- Sub -> Main -> Hook(HTTP POST) -> 웹앱 -> 대표 알림
- 긴급도, 출처, 내용을 포함

#### 승인 처리
- 대표가 승인/반려/수정 지시
- 대표는 Main에게만 지시 (Sub 직접 지시 불가)
- 승인 없이 다음 단계 진행 불가
- 모든 이력 DB에 저장

### 1.4 상태 관리

#### 노트 기반 상태 (.orchestrator/)
- 오케스트레이터가 읽고 이어서 작업하는 컨텍스트
- `main-context.md`, `sub-contexts/`, `decisions/`, `progress/`
- Claude Code Hooks가 작업 시점마다 자동 업데이트
- 에이전트의 "인수인계 문서" 역할

#### DB 기반 상태 (SQLite)
- 대시보드가 빠르게 조회하는 구조화된 상태
- 에이전트 트리, 승인 큐, 비용 집계, 알림
- 대시보드의 "조회용 데이터 소스" 역할

#### 이중 저장
- Hooks 이벤트 발생 시 노트 + DB 양쪽에 동시 기록
- 노트와 DB는 역할이 다르며 상호 보완

### 1.5 데이터 민감도

| 등급 | 설명 | 저장 방식 |
|---|---|---|
| 극민감 | 암호화 필수 데이터 (API 키, 금융 정보 등) | 암호화 저장 |
| 민감 | 로컬 전용 데이터 (개인 정보 등) | 로컬 저장, 외부 전송 금지 |
| 일반 | 기본 저장 데이터 (프로젝트 진행 상태 등) | 기본 저장 |

### 1.6 외부 연동

#### AI Gateway (LiteLLM)
- 모든 모델 호출의 단일 진입점
- 100+ 모델 지원
- 직접 API 호출 금지

#### MCP 커넥터 레이어
- 외부 서비스 연동 시 반드시 경유
- 금융 쓰기 API는 구조적으로 영구 차단

### 1.7 메타버스 UI (가상 오피스)

#### 메타 공간
- 대시보드를 가상 오피스 공간으로 구성
- Part = 부서 공간, Sub = 팀 공간으로 구역 분리
- 대표실 = 대시보드 메인 뷰

#### 에이전트 캐릭터
- 각 에이전트(Main, Part, Sub, 인스턴스)를 귀여운 캐릭터로 시각화
- 캐릭터 상태가 에이전트 상태를 반영 (작업 중, 대기 중, 오류 등)
- 승인 대기 시 캐릭터가 대표실 앞에서 기다리는 등 상태를 시각적으로 표현
- 상세 컨셉(캐릭터 디자인, 애니메이션 등)은 컨셉 결정 단계에서 구체화

### 1.8 양방향 터미널 제어

#### 웹-CLI 양방향 통신
- tmux + node-pty + Hooks를 통한 stdin/stdout 완전 제어
- 웹앱에서 CLI로 명령/텍스트를 직접 전송 (stdin)
- CLI의 출력(stdout)을 실시간으로 웹앱에 표시
- 인스턴스 상세 뷰에서 양방향 터미널 인터페이스 제공

### 1.9 대표 지시 체계

#### 능동적 지시
- 대표가 승인 처리 외에도 Main에게 능동적으로 새로운 지시를 내리는 채팅/명령 UI
- "이 프로젝트 우선순위 올려", "새 프로젝트 시작해" 등 자유로운 지시
- 대표의 모든 지시 내용과 시각을 이력으로 기록

### 1.10 감사 로그 (Audit Trail)

#### 시스템 행동 감사
- 대표의 모든 행동(지시, 승인, 반려, 설정 변경) 이력 기록
- 에이전트의 모든 주요 행동(태스크 시작/완료, 오류, 의사결정 요청) 이력 기록
- 디버깅, 사후 분석, 책임 추적에 활용

### 1.11 리소스 관리

#### 동시 실행 제한
- Mac 리소스 한계 상 동시 실행 에이전트 수 상한 설정
- 상한 초과 시 큐잉 또는 대표에게 확인 요청
- CPU/메모리 모니터링 기반 자동 제한

### 1.12 데이터 백업

#### 백업/복원 체계
- SQLite DB + .orchestrator/ 파일의 자동/수동 백업
- 자동 백업 주기 설정 가능
- Mac Mini 이전 시 데이터 보전 보장
- 복원 절차 제공

## 2. 도메인 관계도

```
대표 (Human)
  |
  | 지시/승인
  v
[Main 오케스트레이터] ---- (비서실장)
  |
  | Skill로 동적 생성
  v

  |         +-- 승인 정책 (Part별 독립)
  |         +-- 재시도 정책 (Part별 독립)

  |
  | 복수 Sub 관리
  v

  |

  v
```

## 3. 용어 사전 (Glossary)

| 용어 | 정의 |
|---|---|
| **Main 오케스트레이터** | 시스템 최상위 오케스트레이터. 대표의 지시를 받아 Part에 전달하는 비서실장 역할 |
| **Part 오케스트레이터** | 특정 도메인(부서)을 담당하는 오케스트레이터. Skill로만 동적 생성 |
| **Sub 오케스트레이터** | Part 내에서 개별 프로젝트/업무를 담당하는 팀장 역할 |
| **인스턴스** | Sub가 부분 태스크를 외주하는 AI 모델 호출 단위 |
| **Part Skill** | Part를 생성하기 위한 bash 스크립트. 메타데이터 + 입력 스키마 + 실행 로직 |
| **Skill 라이브러리** | Skill 파일들이 저장되는 경로 (`~/.claudemanager/skills/`) |
| **단일 상속** | 자식 Skill이 `source`로 부모 Skill 하나만 로드하는 상속 방식 |
| **schema 모드** | Skill의 입력 스키마를 반환하는 실행 모드 (UI 폼 자동 생성용) |
| **execute 모드** | 입력을 받아 Part를 실제 생성하는 Skill 실행 모드 |
| **Human-in-the-Loop** | 중요 의사결정 시 대표의 승인을 반드시 거치는 흐름 |
| **Hook** | Claude Code Hooks. 이벤트 발생 시 HTTP POST로 웹앱에 알리는 메커니즘 |
| **노트 기반 상태** | `.orchestrator/` 폴더의 마크다운 파일. 오케스트레이터의 인수인계 문서 |
| **이중 저장** | Hooks 이벤트 시 노트(파일)와 DB 양쪽에 동시 기록하는 방식 |
| **데이터 민감도** | 극민감/민감/일반 3단계로 데이터 보호 수준을 분류 |
| **LiteLLM** | 100+ AI 모델을 단일 인터페이스로 호출하는 AI Gateway |
| **MCP 커넥터** | 외부 서비스 연동 시 반드시 경유하는 추상화 레이어 |
| **MODEL_ROUTING** | Part Skill에 정의된 모델 라우팅 설정 필드 |
| **tmux** | 터미널 세션 관리 도구. 에이전트별 세션을 분리 운영 |
| **PM2** | Node.js 프로세스 매니저. 서버 재시작 시 자동 복구에 사용 |
| **메타 공간** | 대시보드를 가상 오피스로 표현한 UI. Part=부서 공간, Sub=팀 공간 |
| **에이전트 캐릭터** | 각 에이전트를 시각적으로 표현하는 캐릭터. 상태에 따라 행동이 변함 |
| **대시보드** | 대표가 전체 AI 조직을 감독하는 웹 UI (대표실) |
| **감사 로그** | 대표와 에이전트의 모든 주요 행동을 시간순으로 기록하는 이력 |
| **양방향 터미널** | 웹앱에서 CLI로 stdin을 전송하고 stdout을 수신하는 완전 제어 인터페이스 |
| **리소스 관리** | 동시 실행 에이전트 수와 시스템 자원을 제한/관리하는 메커니즘 |
| **자동 백업** | SQLite DB와 .orchestrator/ 파일을 주기적으로 자동 백업하는 기능 |
| **승인 정책** | Part별로 독립 설정되는 승인 규칙 (전역 하드코딩 금지) |
| **재시도 정책** | 에이전트 실패 시 자동 재시도 횟수/간격 설정 (Part별 독립) |
| **skill-version.lock** | Skill 실행 시점의 버전을 기록하는 파일 (재현성 보장) |
| **input.json** | Skill 실행 시 입력된 기준 정보를 기록하는 파일 (재현성 보장) |

## 4. 비즈니스 규칙

### 4.1 Skill 규칙
- **BR-SK-01**: Skill : Part = 1 : 1. 같은 Skill로 여러 Part를 생성할 수 없다
- **BR-SK-02**: 단일 상속만 허용. 다중 상속 금지
- **BR-SK-03**: 하드코딩 Part 금지. 모든 Part는 Skill을 통해서만 생성
- **BR-SK-04**: Skill 실행 시 반드시 `skill-version.lock`과 `input.json`을 기록 (재현성)
- **BR-SK-05**: Skill 작성은 대표와 Main 오케스트레이터 대화를 통해 진행

### 4.2 의사결정 규칙
- **BR-DEC-01**: 대표는 Main에게만 지시한다. Sub에 직접 지시하지 않는다
- **BR-DEC-02**: 승인 없이 다음 단계로 진행할 수 없다
- **BR-DEC-03**: 승인 정책은 Part별로 독립 설정한다 (전역 하드코딩 금지)
- **BR-DEC-04**: 모든 승인/반려/수정 지시 이력은 DB에 저장한다

### 4.3 데이터 규칙
- **BR-DAT-01**: 극민감 데이터는 반드시 암호화 저장
- **BR-DAT-02**: 금융 쓰기 API는 구조적으로 영구 차단
- **BR-DAT-03**: 이벤트 발생 시 노트와 DB에 동시 기록 (이중 저장)
- **BR-DAT-04**: 절대 경로 하드코딩 금지, 환경변수 기준

### 4.4 운영 규칙
- **BR-OPS-01**: 오케스트레이터(Main, Part, Sub)는 반드시 Claude Code로 실행
- **BR-OPS-02**: 모든 모델 호출은 LiteLLM을 경유 (직접 API 호출 금지)
- **BR-OPS-03**: 외부 연동은 MCP 커넥터 레이어를 경유
- **BR-OPS-04**: Part 내 Sub 간 독립 운영 (간섭 없음)
- **BR-OPS-05**: 에이전트 실패 시 Part별 재시도 정책에 따라 자동 재시도
- **BR-OPS-06**: 모든 재시도 실패 시 에이전트 정지 + 대표 알림

### 4.5 이식성 규칙
- **BR-MIG-01**: 모든 경로는 환경변수 기준 (`$CLAUDEMANAGER_HOME`, `$PROJECTS_ROOT`, `$SKILL_LIB`)
- **BR-MIG-02**: Skill 라이브러리 경로는 `~/.claudemanager/skills/`로 고정
- **BR-MIG-03**: 설정은 `.env` 또는 config 파일로 외부화
- **BR-MIG-04**: 마이그레이션 스크립트(`migrate-to-new-machine.sh`)를 MVP 산출물에 포함

### 4.6 감사 로그 규칙
- **BR-AUD-01**: 대표의 모든 지시/승인/반려/설정 변경은 감사 로그에 기록한다
- **BR-AUD-02**: 에이전트의 주요 행동(태스크 시작/완료, 오류, 의사결정 요청)은 감사 로그에 기록한다
- **BR-AUD-03**: 감사 로그는 삭제할 수 없다 (추가 전용)

### 4.7 리소스 관리 규칙
- **BR-RES-01**: 동시 실행 에이전트 수는 설정된 상한을 초과할 수 없다
- **BR-RES-02**: 상한 초과 시 새 에이전트는 큐에 대기하거나 대표에게 확인을 요청한다
- **BR-RES-03**: CPU/메모리가 임계값을 초과하면 새 에이전트 생성을 자동 제한한다

### 4.8 백업 규칙
- **BR-BAK-01**: SQLite DB와 .orchestrator/ 파일은 설정된 주기로 자동 백업한다
- **BR-BAK-02**: 백업본에서 시스템을 복원할 수 있는 절차를 제공한다
- **BR-BAK-03**: Mac Mini 이전 시 데이터 무결성을 보장한다

### 4.9 대표 지시 규칙
- **BR-CMD-01**: 대표는 Main에게만 능동적 지시를 내린다 (Sub 직접 지시 불가)
- **BR-CMD-02**: 대표의 모든 지시 내용과 시각은 이력으로 기록한다
