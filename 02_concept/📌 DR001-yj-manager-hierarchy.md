## 1. 결정 배경 (Context)

> 최초 작성본은 "YJ Manager 생태계 내 ClaudeManager의 위치"로 잘못 프레이밍되어 있었음 (이 경우 ClaudeManager가 다른 프로그램(MyLife Friend/Location 등)을 총괄하는 메타 레이어로 해석됨). 실제로는 **ClaudeManager 내부의 관리 책임 분담**에 관한 결정.

대표가 기술한 "프로그램 관리(ui, data) / 프로그램 전체 관리(ui, db) / 프로젝트 내 프로그램 관리(ui, data)" 3역할은 **ClaudeManager라는 하나의 프로그램 안**에서 **Main**·**ClaudeManager 전체(=대시보드/DB)**·**Sub(개별 프로젝트)** 가 각기 다른 책임을 진다는 의미.

YJ Manager는 ClaudeManager의 **외부 접근 권한 원천**으로 존재하되, ClaudeManager가 YJ Manager의 다른 자매 프로그램(MyLife Friend, Location 등)을 총괄 관리하지는 않는다.

## 3. 결정 — 3계층 역할 분담

| 계층 | 책임 | 저장소 | 사용자 대화 접점 |
|---|---|---|---|
| **Main** | 프로그램(프로젝트) 관리 — 프로젝트별 Sub CLI 구성, Skill/문서 레이아웃 정비 | UI + **data** (파일) | **초기 구성 시에만** CLI로 대화. 구성 완료 후에는 개입하지 않음 |
| **ClaudeManager 전체** | 프로그램 전체 관리 — 웹 대시보드, 상태/비용/이력/리포트 종합 | UI + **DB** (SQLite) | 웹 대시보드 (감독·모니터링 뷰, 직접 CLI 대화 없음) |
| **Sub (프로젝트별)** | 해당 프로젝트 내 프로그램 관리 — 프로젝트 수행 실무 | UI + **data** (프로젝트 내 파일) | **구성 이후 사용자의 주 대화 접점**. 사용자 ↔ Sub CLI 직접 대화로 진행 |

### 외부 경계 (YJ Manager 권한)
- YJ Manager는 ClaudeManager의 접근 권한 원천. YJ Manager가 연결한 프로젝트 폴더 범위 내에서만 ClaudeManager가 동작.
- ClaudeManager는 하나의 프로그램으로, 다른 YJ Manager 자매 프로그램(MyLife Friend, Location, Finance Bot 등)과 **동등 레벨**. 서로를 총괄하지 않는다.

## 4. 사용 흐름

```
[1단계 · 프로젝트 구성 — Main 단계]
사용자 → Main CLI → "프로젝트 X 시작"
Main → Sub CLI 생성 + Skill/문서 레이아웃 준비 + .orchestrator 구조 생성

[2단계 · 프로젝트 수행 — Sub 단계]
사용자 → Sub CLI 직접 대화 → Sub가 프로젝트 진행
 (Main은 이 시점에 개입 ✗)

[3단계 · 감독·비용·이력 — ClaudeManager 전체 단계]
사용자 → 웹 대시보드 → 여러 Sub의 상태·비용·이력·리포트 종합 확인
 (필요 시 Sub 상세 팝업에서 CLI/Note/Log 열람)
```

---

## 5. 저장소 분리 이유

- **Main/Sub가 data(파일)를 쓰는 이유**: Claude Code CLI가 직접 읽고 쓸 수 있어야 토큰 낭비 없이 상태를 유지하고, PM2 재시작 시 `.orchestrator/*.md`에서 복구 가능.
- **ClaudeManager 전체가 DB(SQLite)를 쓰는 이유**: 다수 Sub의 상태·비용·이력을 조인·집계·시계열 분석해야 하는 대시보드는 파일만으로 불가. DB는 파생 뷰.
- 결과: **data = 진실 소스, DB = 파생 뷰**. Hooks가 이중 기록.

| 감독 일관성 | ✅ Main이 모두 앎 | △ 대시보드(DB)가 담당 | ✗ |
