## SC-001. 최초 접속 및 온보딩

**제목**: 처음 ClaudeManager에 접속하여 첫 부서를 생성하는 흐름
**전제조건**: 서버가 실행 중이고 Main 오케스트레이터만 가동된 상태. Part는 하나도 없음.
**사용자 목표**: 시스템을 처음 접속하여 구조를 이해하고, 첫 Part(프로젝트부)를 생성한다.
**관련 기능**: [F008, F013, F018, F028, F059]

### 상세 흐름

**Step 1. 로그인 및 첫 화면**

1. 대표가 PC 브라우저에서 ClaudeManager 웹앱에 접속한다
2. 로그인 화면이 표시된다. 대표가 비밀번호를 입력하여 인증한다
3. 화면 전환: 로그인 화면이 페이드아웃되며 워크스페이스 뷰가 천천히 밝아지며 나타난다

**Step 2. 워크스페이스 뷰 — 빈 워크스페이스 첫인상**

4. 3D 카툰 워크스페이스 뷰가 펼쳐진다. 파스텔 톤 + 소프트 라이팅의 빈 워크스페이스 공간이 보인다
5. 공유 워크스페이스에 나의 아바타(2~3등신 로우폴리 3D 카툰)가 데스크에 앉아있다
6. 옆자리에 Main(비서실장) 캐릭터가 앉아있다 — 정장 + 안경, 대기 모션(손을 앞으로 모으고 서 있음)
7. Main 캐릭터 머리 위에 말풍선이 나타난다: "환영합니다!" (2초 후 사라짐)
8. 내 데스크 주변은 텅 빈 공간 — 아직 어떤 부서도 없다. 바닥에 점선 테두리로 "부서 공간 예정지"가 희미하게 표시된다
9. 하단 바에 "에이전트: 1/10", 비용: $0.00, 헬스: 정상(초록)이 표시된다

**Step 3. Main에 접촉 — 온보딩 대화**

10. 대표가 워크스페이스 뷰에서 Main(비서실장) 캐릭터에 다가가 접촉한다
11. 접촉 시 채팅 패널이 슬라이드인으로 열린다. 상단에 Main 캐릭터 아이콘 + "비서실장" 이름이 표시된다

> 💬 **Main**: "안녕하세요, 대표님. 비서실장입니다. 워크스페이스가 아직 비어있네요. 첫 부서를 만들어볼까요?"
> 💬 **대표**: "그래, 어떤 부서를 만들 수 있어?"
> 💬 **Main**: "현재 준비된 부서 유형은 프로젝트관리부입니다. 개발 프로젝트를 체계적으로 진행할 수 있는 부서입니다. 추후 재무관리부, 일상관리부 등도 추가할 수 있습니다."
> 💬 **대표**: "프로젝트관리부부터 만들자"
> 💬 **Main**: "프로젝트관리부 설립을 준비하겠습니다. 먼저 대표님의 프로젝트 진행 방식을 파악해야 합니다. Skill 설정 화면으로 안내할까요?"
> 💬 **대표**: "응 안내해줘"
> 💬 **Main**: "Skill 실행 화면으로 이동합니다. 몇 가지 질문을 드리겠습니다."

12. 대표가 승인하면, Skill 실행 화면(SC-002)으로 자연스럽게 연결된다

### 기대결과
- 빈 워크스페이스에 비서실장만 서있는 모습을 보며, 이제부터 이 공간이 채워질 것이라는 기대감을 느낀다
- 채팅 기반 인터랙션이 직관적으로 이해된다
- 첫 Skill 실행으로 자연스럽게 유도된다

### 대표 경험
- 빈 워크스페이스에 비서실장만 대기하고 있는 모습에서 **"여기가 내 AI 조직의 시작이구나"** 라는 설렘을 느낀다
- 채팅으로 자연스럽게 대화하며 시스템의 구조를 이해하게 되어 **별도의 튜토리얼 없이도** 무엇을 해야 할지 직관적으로 파악한다
- 부서 공간 예정지의 점선 테두리를 보며 조직 확장의 가능성을 상상한다

### UI 전환 묘사
- **로그인 -> 워크스페이스 뷰**: 로그인 화면 페이드아웃 -> 워크스페이스 뷰 페이드인 (0.5초)
- **Main 접촉 -> 채팅 패널**: 워크스페이스 뷰에서 Main 캐릭터에 접촉하면 채팅 패널이 오른쪽에서 슬라이드인
- 데스크톱: 워크스페이스 뷰 위에 채팅 패널이 오버레이로 표시
- 모바일: Main에 접촉하면 채팅 전체 화면으로 전환

## SC-002. Part 생성 (Skill 실행)

**제목**: 도메인별 Skill을 실행하여 Part(부서)를 동적 생성하는 흐름
**전제조건**: Main 오케스트레이터가 가동 중. Skill 라이브러리에 base-part.sh, project-part.sh가 등록되어 있음. 워크스페이스에는 아직 Part가 없거나 기존 Part만 있는 상태.
**사용자 목표**: 도메인(재무관리, 일상관리, 프로젝트관리, 업무관리 등) 전용 Skill을 실행하여 해당 도메인의 Part(부서)를 생성한다. Skill은 도메인별 프로젝트 생성·관리의 표준 템플릿 역할을 하며, 이를 통해 도메인 내 모든 프로젝트가 동일한 구조로 표준화된다.
**관련 기능**: [F001, F002, F003, F004, F005, F006, F009, F044, F045]

### Part와 Skill의 관계

```
Skill 라이브러리 (~/.claudemanager/skills/)
├── base-part.sh          ← 모든 Skill의 부모 (공통 로직)
├── project-part.sh       ← 프로젝트 관리 도메인 (source base-part.sh)
├── finance-part.sh       ← 재무 관리 도메인 (추후 대표가 작성)
├── daily-part.sh         ← 일상 관리 도메인 (추후 대표가 작성)
└── work-part.sh          ← 업무 관리 도메인 (추후 대표가 작성)

각 Skill이 생성하는 Part(부서):
project-part.sh  →  🏭 프로젝트관리부  → 하위에 개발 프로젝트들을 Sub로 운영
finance-part.sh  →  🏦 재무관리부      → 하위에 투자, 가계부 등을 Sub로 운영
daily-part.sh    →  🏠 일상관리부      → 하위에 건강, 루틴 등을 Sub로 운영
work-part.sh     →  🏢 업무관리부      → 하위에 업무 프로젝트들을 Sub로 운영
```

### Skill이 정의하는 것 (부서 설립 매뉴얼)

```
Skill = 부서 설립 매뉴얼 전체
├── 1. 도메인 방법론 — 어떤 프로세스로 일하는가 (작업 순서, 산출물)
├── 2. 팀 구성 — 어떤 인스턴스들이 필요한가 (역할 목록)
├── 3. 인스턴스별 역할 정의 — 누가 무엇을 어떻게 하는가 (업무 방식, 사용 모델)
├── 4. 정책 — 승인, 재시도, 민감도
└── 5. 기술 설정 — 폴더, Hooks, 모델 라우팅
```

**Skill을 도메인별로 분리하는 이유**: 도메인마다 방법론, 팀 구성, 인스턴스 역할, 승인 정책이 모두 다르다. Skill로 표준화하면 같은 도메인 내 모든 프로젝트가 동일한 팀 구성·작업 방식으로 생성되어 관리가 용이하다.

### 상세 흐름

**Step 1. 대표가 채팅으로 새 부서 필요를 말한다 → Main과 방법론 탐색 시작**

**Step 2. Main이 대화 내용을 기반으로 Skill을 자동 생성한다**

> Main은 대표와의 대화에서 확정된 방법론, 팀 구성, 인스턴스 역할을 `project-part.sh` 스크립트로 코드화한다. 생성된 Skill은 `~/.claudemanager/skills/`에 등록된다. 이 과정은 Main이 자동으로 수행하며 대표는 기다리기만 하면 된다.

> 💬 **Main**: "project-part.sh Skill 생성이 완료되었습니다. Skill 라이브러리에 등록했습니다. 이제 이 Skill로 프로젝트관리부를 설립하겠습니다."

**Step 3. Skill 스키마 기반 입력 폼이 표시된다**

1. 시스템이 `project-part.sh`를 **schema 모드**로 실행한다

> Skill의 schema 모드란: Skill 스크립트를 `./project-part.sh schema`로 실행하면, "이 Skill을 실행하려면 어떤 정보가 필요한지"를 JSON으로 응답하는 기능이다.
> ```json
> {
>   "fields": [
>     { "name": "part_name", "label": "Part명", "type": "text", "required": true },
>     { "name": "description", "label": "설명", "type": "text", "required": false },
>     { "name": "sensitivity", "label": "민감도", "type": "select", "options": ["극민감", "민감", "일반"], "required": true },
>     { "name": "approval_policy", "label": "승인 정책", "type": "text", "required": true },
>     { "name": "retry_count", "label": "재시도 횟수", "type": "number", "default": 3 },
>     { "name": "retry_strategy", "label": "재시도 전략", "type": "select", "options": ["지수백오프", "고정간격"] },
>     { "name": "model_routing", "label": "기본 모델", "type": "select", "options": ["claude-sonnet", "claude-haiku"] }
>   ]
> }
> ```
> 웹앱은 이 JSON을 읽고 **자동으로 입력 폼 UI를 생성**한다. 이 방식 덕분에 새 Skill을 추가할 때 프론트엔드 코드 수정이 필요 없다. 예를 들어 추후 `finance-part.sh`를 만들면 "투자 유형", "위험 등급" 같은 필드를 schema에 정의해두면 웹앱이 알아서 해당 폼을 표시한다.

2. 스키마 기반 입력 폼이 자동 생성되어 화면에 표시된다:

| 필드 | 입력값 예시 | 설명 |
|---|---|---|
| Part명 | 프로젝트관리부 | 워크스페이스에 표시될 부서 이름 |
| 설명 | SW 개발 프로젝트 관리 | 부서 역할 설명 |
| 민감도 등급 | 일반 | 극민감/민감/일반 중 선택 |

1. 기획 인스턴스가 PRD 작성을 완료한다
2. 워크스페이스 뷰에서 기획 인스턴스 캐릭터가 타이핑을 멈추고 기쁨 점프 모션을 보인다. 머리 위에 "완료!" 말풍선 표시
3. Sub(팀장)가 결과물을 확인하고, 승인 정책(approval-policy.md)에 따라 대표 승인이 필요하다고 판단한다
4. Sub -> Part -> Main으로 승인 요청이 전달된다
5. Main(비서실장) 캐릭터가 프로젝트관리부 공간에서 내 캐릭터에게 다가오는 이동 모션 (1.5초)
6. 내 캐릭터에 도착한 Main이 접촉하여 승인 팝업을 띄운다
7. Main 캐릭터 머리 위에 노란색 "결재 요청" 말풍선이 표시된다
8. 대시보드 상단에 빨간 알림 뱃지가 나타난다: "1"
9. 브라우저 푸시 알림: "비서실장: 프로젝트부에서 결재가 올라왔습니다"

**Step 2. 대표가 승인 팝업에서 승인 요청을 확인한다**

10. Main이 접촉하여 띄운 승인 팝업에서 상세 내용을 확인한다
11. 승인 팝업 상단에 "승인 대기 1건" 노란색 배너 표시. 채팅 패널도 함께 열림

> 💬 **Main**: "프로젝트부 할일관리앱 팀에서 기획 단계가 완료되어 결재를 올렸습니다. PRD와 기능 목록이 작성되었습니다. 확인 부탁드립니다."
> 💬 **대표**: "PRD 내용을 요약해줘"
> 💬 **Main**: "할일관리앱 PRD 요약입니다:
> - 핵심 기능: 할일 CRUD, 우선순위 정렬, 카테고리 분류, 마감일 알림
> - 기능 수: 12개
> - 예상 개발 기간: 3일
> - 타겟: 개인 생산성 관리
> 
> 전체 PRD는 대시보드 리포트 섹션에서 확인하실 수 있습니다. 승인하시겠습니까?"
> 💬 **대표**: "기능이 좀 부족한데. 반복 일정 기능도 추가해줘"
> 💬 **Main**: "반복 일정 기능을 추가하겠습니다. 기획 인스턴스에 수정 지시를 전달합니다. 수정 완료 후 다시 보고드리겠습니다."

12. Main이 Part를 통해 Sub에게 수정 지시를 전달한다
13. 워크스페이스 뷰에서 Main 캐릭터가 내 캐릭터 옆에서 자기 자리로 돌아가는 이동 모션
14. 기획 인스턴스 캐릭터가 다시 타이핑 모션을 시작한다. 머리 위에 "수정 중" 말풍선

**Step 3. 수정 후 재승인**

15. (시간 경과) 기획 인스턴스가 수정을 완료한다
16. 다시 승인 요청이 올라온다 — Main 캐릭터가 다시 내 캐릭터에게 다가와 접촉하여 승인 팝업을 띄운다

> 💬 **Main**: "수정이 완료되었습니다. 반복 일정 기능이 추가되어 기능 수가 14개로 늘었습니다. 재확인 부탁드립니다."
> 💬 **대표**: "좋아, 승인"
> 💬 **Main**: "승인이 처리되었습니다. 프로젝트부에 전달하여 디자인 단계를 시작하겠습니다."

17. 시스템이 승인 이력(수정 지시 1회 + 최종 승인, 코멘트, 처리 시각)을 DB에 저장한다
18. .orchestrator/decisions/에 의사결정 내용이 기록된다
19. 워크스페이스 뷰에서 Main 캐릭터가 제자리로 돌아간다
20. Sub(팀장) 캐릭터가 기쁨 점프 모션을 보인다
21. 기획 인스턴스 캐릭터가 노트북을 닫고 팀 구역에서 퇴장한다 (퇴근 모션)
22. 새로운 디자인 인스턴스 캐릭터가 등장하여 작업을 시작한다

### 기대결과
- 승인 요청이 워크스페이스 뷰(Main이 다가와 접촉하여 팝업) + 채팅 패널(상세 보고) + 푸시 알림으로 다중 전달된다
- 대표의 수정 지시/승인이 에이전트 조직에 즉시 반영된다
- 모든 승인 이력(수정 지시 포함)이 DB에 저장되어 추후 조회 가능하다

### 대표 경험
- Main이 내 캐릭터에게 다가와 접촉하여 승인 팝업을 띄우는 모습에서 **"진짜 동료가 결재를 올리는 것 같다"** 는 공존감을 느낀다
- 채팅으로 "요약해줘"라고 하면 바로 정리해주고, 수정 사항을 말하면 바로 반영해주는 **자연스러운 대화형 의사결정** 경험
- 승인 후 캐릭터들이 기뻐하고 다음 단계로 넘어가는 모습에서 **프로젝트가 진행되는 리듬감**을 느낀다

### UI 전환 묘사
- **Main 접촉 -> 승인 팝업**: Main이 접촉하면 승인 팝업이 자동으로 열림. 승인 요청 메시지로 자동 스크롤
- 데스크톱: 워크스페이스 뷰에서 다가오는 모션을 보면서 승인 팝업에서 동시에 내용 확인 가능
- 모바일: 푸시 알림 탭 -> 채팅 화면으로 바로 이동. 승인 메시지 하단에 "승인/반려" 버튼 표시

## SC-005. 에이전트 활동 열람 (팝업 모달)

**제목**: 워크스페이스 뷰에서 캐릭터에 다가가 접촉하여 에이전트의 상세 활동을 확인하는 흐름
**전제조건**: SC-003에서 시작된 프로젝트가 진행 중이며, 여러 에이전트가 작업 중인 상태.
**사용자 목표**: 특정 에이전트의 대화 내용, 노트, 로그, 터미널을 상세히 확인한다.
**관련 기능**: [F014, F015, F040, F057, F058, F062]

### 상세 흐름

**Step 1. 워크스페이스 뷰에서 캐릭터에 다가가 접촉한다**

1. 대표가 워크스페이스 뷰에서 프로젝트관리부 공간을 살펴본다
2. 할일관리앱 팀 구역에서 Sub(팀장) 캐릭터가 감독 모션을 보이고, 개발 인스턴스 캐릭터가 타이핑 모션을 보인다
3. 대표가 Sub(팀장) 캐릭터에 다가가 접촉한다
4. 접촉 시 캐릭터 주변에 선택 하이라이트 이펙트(파란 원형 테두리)가 나타난다

**Step 2. 팝업 모달이 열린다**

5. 워크스페이스 뷰 위에 화면 80% 크기의 팝업 모달이 슬라이드업 애니메이션으로 열린다 (0.3초)
6. 모달 뒤의 워크스페이스 뷰는 어두워진다 (반투명 오버레이)
7. 모달 상단에 표시되는 정보:
   - 캐릭터 아이콘 (부서 색상 유니폼 + 팀 배지)
   - 이름: "할일관리앱 팀장"
   - 역할: Sub 오케스트레이터
   - 현재 상태: "개발 단계 감독 중" (초록 상태 뱃지)
   - 가동 시간: "2시간 15분"

**Step 3. 탭 1 — 대화 내용 확인**

8. 탭 1(대화)이 기본 표시된다. Sub의 대화 이력이 시간순으로 나열된다:
   - [14:00] Part -> Sub: "할일관리앱 프로젝트를 시작하라. 방법론에 따라 기획부터 진행."
   - [14:05] Sub -> 기획 인스턴스: "요구사항 분석 후 PRD를 작성하라."
   - [15:30] 기획 인스턴스 -> Sub: "PRD 초안 완료. 기능 14개 도출."
   - [15:35] Sub -> Part: "기획 단계 완료. 대표 승인 요청."
   - [16:00] Part -> Sub: "대표 승인 완료. 디자인 단계 시작."
   - [16:05] Sub -> 디자인 인스턴스: "PRD 기반 화면 정의서를 작성하라."

**Step 4. 탭 2 — 노트 확인**

9. 대표가 탭 2(노트)를 선택한다
10. .orchestrator/parts/project/subs/todo-app/ 하위 노트가 마크다운으로 렌더링된다:
    - sub-context.md — 현재 상태 요약 (현재 단계, 시작일, 담당 인스턴스)
    - progress/ — 단계별 진행 타임라인 (완료된 단계는 초록, 진행 중은 파란, 미시작은 회색)
    - decisions/ — 의사결정 카드 목록

**Step 5. 탭 3 — 로그 확인**

11. 대표가 탭 3(로그)를 선택한다
12. Hooks 수집 이벤트 로그가 타임라인으로 표시된다:
    - [14:00:00] SubStarted — 할일관리앱 Sub 시작
    - [14:00:05] InstanceCreated — 기획 인스턴스 생성 (claude-opus)
    - [14:00:06] TokenUsage — 입력: 2,500 / 출력: 1,200 / 비용: $0.03
    - [15:30:00] StageCompleted — 기획 단계 완료
    - [16:05:00] InstanceCreated — 디자인 인스턴스 생성 (claude-opus)

**Step 6. 탭 4 — 터미널 (양방향 제어)**

13. 대표가 탭 4(터미널)를 선택한다
14. xterm.js 기반 실시간 터미널 화면이 표시된다. 현재 Sub 에이전트의 tmux 세션이 연결된다
15. 터미널에 에이전트의 stdout/stderr가 실시간으로 스트리밍된다
16. 대표가 터미널 하단 입력창에 명령어를 입력하여 stdin으로 전송할 수 있다 (양방향 제어)
17. ESC 키 또는 모달 바깥 터치로 팝업을 닫는다. 슬라이드다운 애니메이션으로 닫힘 (0.3초)

**Step 7. 다른 에이전트 탐색**

> 💬 **대표**: "개발 인스턴스가 뭘 하고 있는지 확인하고 싶어"
> 💬 **Main**: "워크스페이스 뷰에서 개발 인스턴스 캐릭터에 다가가 접촉하시면 상세 정보를 확인할 수 있습니다. 현재 개발 인스턴스는 화면 정의서 기반으로 코드를 작성 중입니다."

18. 대표가 워크스페이스 뷰에서 개발 인스턴스 캐릭터에 다가가 접촉한다
19. 인스턴스 팝업 모달이 열린다 — 탭 4(터미널)가 기본 활성화, 코드 작성 과정이 실시간으로 보인다

### 기대결과
- 에이전트의 전체 활동을 대화/노트/로그/터미널 4개 탭에서 종합적으로 확인할 수 있다
- 양방향 터미널 제어로 필요 시 직접 개입할 수 있다
- 계층별(Main/Part/Sub/인스턴스) 열람 내용이 다르다

### 대표 경험
- 캐릭터에 다가가 접촉하면 바로 상세 정보가 나오는 **직관적인 탐색** 경험
- 대화 탭에서 지시가 어떻게 분배되었는지, 노트 탭에서 결정사항이 어떻게 정리되었는지, 터미널에서 실제 작업이 어떻게 수행되는지를 **한 화면에서 종합적으로** 파악할 수 있는 통제감
- "내 조직이 어떻게 일하고 있는지 투명하게 볼 수 있다"는 신뢰감

### UI 전환 묘사
- **캐릭터 접촉 -> 팝업 모달**: 접촉 즉시 캐릭터 위치에서 모달이 확장되는 애니메이션 (0.3초 슬라이드업)
- **모달 닫기**: ESC 또는 바깥 터치 -> 슬라이드다운 + 페이드아웃 (0.3초)
- **탭 전환**: 탭 선택 시 내용이 크로스페이드로 전환 (0.2초)
- 데스크톱: 모달이 화면 80% 크기
- 모바일: 이 기능은 데스크톱 전용. 모바일에서 캐릭터 상세는 제공하지 않음 (간소 상태 카드로 대체)

## SC-006. 오류 발생, 자동 재시도 및 실패

**제목**: 인스턴스에서 오류가 발생하여 자동 재시도 후 최종 실패하는 흐름
**전제조건**: SC-003에서 시작된 프로젝트의 개발 인스턴스가 작업 수행 중. Part별 재시도 정책: 3회, 지수 백오프(10초/30초/90초).
**사용자 목표**: 오류 상황을 인지하고, 재시도 과정을 관찰하며, 최종 실패 시 적절한 조치를 취한다.
**관련 기능**: [F032, F033, F034, F035, F028, F029, F030, F062]

### 상세 흐름

**Step 1. 오류 발생 — 워크스페이스 뷰 캐릭터 반응**

1. 개발 인스턴스가 API 호출 중 타임아웃 오류가 발생한다
2. 오류 로그(에러 메시지, 스택 트레이스, 발생 시각)가 DB에 저장된다
3. 워크스페이스 뷰에서 해당 인스턴스 캐릭터의 변화:
   - 타이핑 모션이 멈춘다
   - 머리 위에 ❗ 이모지가 나타난다 (빨간색 + 깜빡임)
   - 당황 모션: 고개를 좌우로 흔들며 손을 허둥지둥 (0.5초 반복)
4. Sub(팀장) 캐릭터가 인스턴스 쪽으로 고개를 돌리는 모션

**Step 2. 자동 재시도 과정 — 단계별 캐릭터 연출**

5. Part별 재시도 정책(retry-policy.md)에 따라 1차 자동 재시도 실행 (10초 후)
   - 인스턴스 캐릭터 머리 위: ❗ -> "재시도 1/3" 말풍선
   - 캐릭터가 다시 타이핑 모션을 시작
6. 1차 재시도 실패
   - 캐릭터가 다시 당황 모션. 머리 위: "재시도 실패 1/3"
7. 2차 재시도 실행 (30초 후) -> 실패
   - 머리 위: "재시도 실패 2/3"
8. 3차(최종) 재시도 실행 (90초 후) -> 실패
   - 캐릭터가 완전히 멈춘다. 회색 오버레이 적용
   - 머리 위에 빨간 X 마크가 지속 표시
   - Sub(팀장) 캐릭터 머리 위에도 ❗ 표시

**Step 3. Main이 대표에게 보고 — 채팅 대화**

9. 대시보드 상단에 빨간 알림 뱃지: "오류 1"
10. 브라우저 푸시 알림: "비서실장: 프로젝트부에서 문제가 발생했습니다. 확인 부탁드립니다"

> 💬 **Main**: "프로젝트부 할일관리앱 팀의 개발 인스턴스에서 오류가 발생했습니다. 재시도 중입니다. (1/3)"
> (10초 후)
> 💬 **Main**: "1차 재시도 실패. 계속 시도합니다. (2/3)"
> (30초 후)
> 💬 **Main**: "2차 재시도 실패. 마지막 시도를 합니다. (3/3)"
> (90초 후)
> 💬 **Main**: "모든 재시도가 실패했습니다. 개발 인스턴스가 정지되었습니다.
> - 오류 유형: API 타임아웃
> - 오류 메시지: `Connection timed out after 30000ms`
> - 재시도: 3/3 모두 실패
> - 영향: 개발 단계 중단
> 
> 터미널을 열어 직접 확인하시겠습니까?"
> 💬 **대표**: "열어줘"
> 💬 **Main**: "개발 인스턴스의 터미널을 열겠습니다."

**Step 4. 대표가 터미널에서 확인하고 조치를 지시한다**

11. 워크스페이스 뷰에서 해당 인스턴스 캐릭터를 자동 선택 -> 팝업 모달 터미널 탭이 열린다
12. 터미널에서 오류 로그를 확인한다
13. 대표가 조치를 결정한다

> 💬 **대표**: "네트워크 문제인 것 같아. 인스턴스를 다시 만들어줘"
> 💬 **Main**: "개발 인스턴스를 재생성하겠습니다. 기존 작업 진행분은 노트에 저장되어 있어 이어서 진행할 수 있습니다."
> 💬 **대표**: "좋아"
> 💬 **Main**: "개발 인스턴스가 재생성되었습니다. 이전 작업 지점(코드 구현 40%)에서 이어서 시작합니다."

14. 워크스페이스 뷰에서 정지된 인스턴스 캐릭터가 사라지고, 새 인스턴스 캐릭터가 등장하여 타이핑 모션을 시작한다. 머리 위에 "작업 재개" 말풍선

### 기대결과
- 자동 재시도 과정이 워크스페이스 뷰 캐릭터 연출 + 채팅 실시간 보고로 투명하게 전달된다
- 최종 실패 시 에이전트가 정지되고 대표에게 즉시 알림이 전달된다
- 노트 기반 복구로 재생성 시 작업 연속성이 보장된다
- 모든 오류/재시도 과정이 로그에 기록된다

### 대표 경험
- 캐릭터의 당황 모션과 ❗ 표시로 오류를 **직관적으로 즉시 인지**한다
- Main이 재시도 과정을 실시간으로 보고해주어 **상황 파악이 즉각적**이다
- 터미널을 열어 직접 확인할 수도 있고, Main에게 지시만 해도 되는 **선택적 개입** 경험
- 재생성 후 이전 작업 지점에서 이어가는 것을 보며 **"작업이 날아가지 않는구나"** 라는 안정감

### UI 전환 묘사
- **워크스페이스 뷰**: 오류 발생 시 해당 캐릭터에 시선을 유도하는 빨간 펄스 이펙트
- **채팅 패널**: 오류 메시지는 빨간 테두리로 강조 표시
- **팝업 모달 자동 오픈**: Main이 터미널을 열겠다고 할 때, 팝업 모달이 자동으로 열리며 터미널 탭이 활성화
- 모바일: 워크스페이스 뷰 없이 채팅으로만 오류 보고 수신. 터미널은 데스크톱 전용

### 예외흐름

> 인스턴스 캐릭터 머리 위: ❗ -> "복구!" 말풍선 -> 정상 타이핑 모션으로 복귀
> 💬 **Main**: "개발 인스턴스에서 일시적 오류가 발생했으나 자동 재시도로 복구되었습니다. 작업을 정상 진행 중입니다."

**E2. API 키 만료로 인한 인증 오류**
> 💬 **Main**: "개발 인스턴스에서 API 인증 오류가 발생했습니다. API 키가 만료되었을 수 있습니다. 키를 확인해주시겠어요?"
> -> SC-011 API 키 관리 흐름으로 연결

**E3. 대표가 프로젝트 자체를 중단하기로 결정**
> 💬 **대표**: "이 프로젝트는 일단 멈춰"
> 💬 **Main**: "할일관리앱 프로젝트를 일시정지하겠습니다. 현재 상태를 노트에 저장합니다."

## SC-007. 비용 모니터링 및 임계값 관리

**제목**: 비용 대시보드에서 API 사용 비용을 확인하고, 임계값 초과 알림에 대응하는 흐름

**관련 기능**: [F016, F022, F031, F037, F044, F045, F046]

3. 비용 대시보드 표시 내용:

## SC-008. 리포트 열람

**제목**: 대시보드 리포트 섹션에서 프로젝트 진행 보고서와 의사결정 이력을 열람하는 흐름
**전제조건**: SC-003~SC-007을 거치며 프로젝트가 개발 단계까지 진행됨. .orchestrator/ 노트에 진행 상황, 의사결정, 비용 데이터가 축적됨.
**사용자 목표**: 구조화된 리포트를 통해 프로젝트 현황과 과거 의사결정을 파악한다.
**관련 기능**: [F013, F014, F025, F040, F041, F061, F063]

### 상세 흐름

**Step 1. 대시보드 리포트 섹션 진입**

1. 대표가 상단 메뉴에서 "대시보드" 탭을 선택하고 리포트 섹션을 연다
2. UI 전환: 기존 뷰에서 대시보드로 전환. 단순 마크다운 뷰어가 아닌 카드형 리포트 UI가 표시된다
3. 좌측에 Part 탭(프로젝트관리부)과 리포트 유형 필터가 표시된다
4. 리포트 목록: 프로젝트 진행 보고서, 의사결정 이력, 비용 리포트, 에이전트 활동 요약, 오류 리포트

## SC-010. 서버 재시작 및 자동 복구

**제목**: 서버가 재시작된 후 시스템이 자동 복구되고 대표에게 알림이 전달되는 흐름
**전제조건**: SC-003~SC-009를 거치며 프로젝트가 개발 단계(60%)에서 진행 중인 상태. 3개 에이전트(Part + Sub + 개발 인스턴스)가 활동 중. Mac Mini가 예기치 않게 재시작됨.
**사용자 목표**: 서버 재시작 후 에이전트들이 자동으로 복구되어 작업을 이어가는 것을 확인한다.
**관련 기능**: [F040, F041, F042, F043, F074]

### 상세 흐름

**Step 1. 서버 재시작 및 자동 복구 프로세스**

1. Mac Mini가 재시작된다 (예: OS 업데이트 자동 재시작)
2. 대표가 웹앱에 접속하면 "서버에 연결할 수 없습니다" 메시지가 표시된다
3. macOS launchd가 PM2를 자동 시작한다
4. PM2가 백엔드 서버를 시작한다
5. 백엔드 복구 순서:
   - .orchestrator/ 폴더를 스캔하여 이전 상태를 파악
   - DB에서 에이전트 트리 구조를 복원
   - tmux 세션을 재생성
   - Claude Code가 각 에이전트의 context.md를 읽고 이어서 작업을 시작
6. 복구 로그가 .orchestrator/system/recovery-log.md에 기록된다

**Step 2. 워크스페이스 뷰 복구 애니메이션**

7. 대표가 웹앱을 새로고침하면 워크스페이스 뷰가 로딩된다
8. 워크스페이스 뷰 복구 연출:
   - 처음에 워크스페이스가 어둡게 표시된다 (정전 느낌)
   - 조명이 하나씩 켜지는 애니메이션 (0.5초씩)
   - 내 데스크 조명 -> 프로젝트관리부 조명 -> 팀 구역 조명 순서
   - Part(부서장) 캐릭터가 책상에 앉으며 나타난다 — 기지개 모션 후 타이핑 시작
   - Sub(팀장) 캐릭터가 나타난다 — 커피 한잔 들고 팀 구역에 앉음
   - 개발 인스턴스 캐릭터가 나타난다 — 노트북을 펼치며 이전 작업을 이어가는 모션
   - 각 캐릭터 머리 위에 순서대로 "복구됨" 말풍선이 표시된다
9. 하단 바: "에이전트: 4/10" (Main + Part + Sub + 인스턴스), 헬스: 정상(초록)

**Step 3. Main이 복구 보고를 한다**

10. 브라우저 푸시 알림: "비서실장: 서버가 재시작되어 복구가 완료되었습니다"

> 💬 **Main**: "서버 재시작 후 자동 복구가 완료되었습니다. 복구 현황입니다:
> | 에이전트 | 상태 | 복구 지점 |
> |---|---|---|
> | 프로젝트관리부 부서장 | 정상 복구 | part-context.md 기반 |
> | 할일관리앱 팀장 | 정상 복구 | sub-context.md 기반 |
> | 개발 인스턴스 | 정상 복구 | 개발 단계 60% 지점 |
> 
> 모든 프로젝트가 중단 지점에서 이어서 진행 중입니다. 서버 중단 시간: 약 3분."
> 💬 **대표**: "데이터 손실은 없어?"
> 💬 **Main**: ".orchestrator/ 노트가 모두 정상입니다. DB와 노트의 정합성을 확인했습니다. 손실된 데이터 없습니다."

> 💬 **Main**: "개발 단계를 이어서 진행하겠습니다."

### 기대결과

## SC-014. 검색 및 필터링

**제목**: 승인 이력, 오류 로그, 비용 내역을 검색하고 필터링하는 흐름
**전제조건**: 시스템이 수주간 운영되어 승인 이력, 오류 로그, 비용 내역이 축적된 상태.

**관련 기능**: [F025, F034, F063, F066, F067]

**Step 1. 리소스 관리 뷰에서 승인 이력 검색**

> |---|---|---|---|

**Step 3. 감사 로그 검색**

## SC-016. 동시 에이전트 리소스 관리

**제목**: 동시 실행 에이전트 수가 상한에 도달하여 큐잉되고, 대표가 설정을 조정하는 흐름

**사용자 목표**: 리소스 제한 상황을 인지하고, 필요 시 상한을 조정한다.
**관련 기능**: [F017, F070, F071, F072, F064, F065]

### 동시 실행 상한 정책
- **기본값**: 10개 (MVP 초기 설정)
- **설정 위치**: 설정 UI → 전역 설정 → "동시 실행 에이전트 상한"
- **조절 범위**: 1~50 (하드웨어 사양에 따라 대표가 판단)
- **리소스 안전장치**: 상한 이내라도 CPU 90% 또는 메모리 90% 초과 시 자동 생성 보류

4. 워크스페이스 뷰 하단 바에 "에이전트: 10/10" 표시, 노란색으로 변경
5. Sub가 11번째 인스턴스를 생성하려 한다
6. 상한 초과로 해당 인스턴스가 대기 큐에 들어간다

> 💬 **Main**: "동시 실행 에이전트 수가 상한(10개)에 도달했습니다. 1개 에이전트가 대기 중입니다. 현재 시스템 상태: CPU 75%, 메모리 68%. 상한을 늘리시겠습니까, 기존 작업 완료 후 자동 시작할까요?"

**Step 2. 대표가 상황을 판단한다**

> 💬 **대표**: "지금 리소스 여유 있네. 상한을 15로 올려줘"
> 💬 **Main**: "동시 실행 상한을 15개로 변경했습니다. 대기 중이던 에이전트를 바로 시작하겠습니다."

10. CPU가 92%에 도달한다
11. 리소스 안전장치가 작동하여 상한(15) 이내임에도 새 에이전트 생성을 자동 보류

## SC-021. 인프라 배포 및 프로세스 관리

**제목**: PM2와 launchd로 시스템을 배포하고 프로세스를 관리하는 흐름
**전제조건**: 개발이 완료되고 빌드된 상태. 또는 SC-020 이전 후 Mac Mini에서 처음 설정하는 상태.
**사용자 목표**: 시스템을 안정적으로 배포하고 프로세스 자동 관리를 설정한다.
**관련 기능**: [F073, F074, F075]

### 상세 흐름

**Step 1. 환경 구성 및 빌드**

1. 대표가 개발 환경 구성 스크립트를 실행한다: `./setup.sh`
   - Node.js 20.x, pnpm, tmux, PM2, Claude Code 자동 설치/확인
   - 누락된 의존성이 있으면 자동 설치 제안
2. 환경변수 파일(.env)을 설정한다:
   ```
   CLAUDEMANAGER_HOME=/Users/user/claudemanager
   PROJECTS_ROOT=/Users/user/projects
   SKILL_LIB=/Users/user/.claudemanager/skills
   DB_PATH=$CLAUDEMANAGER_HOME/data/claudemanager.db
   LITELLM_PORT=4000
   ```
3. 빌드를 실행한다: `pnpm build`

**Step 2. PM2 + launchd 배포**

4. PM2 설정 파일(ecosystem.config.js)을 구성한다
5. PM2로 백엔드를 시작한다: `pm2 start ecosystem.config.js`
6. macOS launchd에 PM2를 등록한다: `pm2 startup launchd`
   - 시스템 부팅 시 PM2 -> 백엔드 자동 시작
7. LiteLLM 프록시를 시작한다: `pm2 start litellm --name litellm`

**Step 3. 정상 동작 확인**

8. 대표가 웹앱(localhost:3000)에 접속한다
9. 워크스페이스 뷰가 정상 표시되고, Main(비서실장) 캐릭터가 나타난다

> 💬 **Main**: "시스템이 정상 시작되었습니다. 모든 서비스가 가동 중입니다:
> - 백엔드 서버: 정상 (port 3000)
> - LiteLLM 프록시: 정상 (port 4000)
> - WebSocket: 연결됨
> - DB: 정상
> 
> 무엇을 도와드릴까요?"

10. 대표가 PM2 모니터링으로 프로세스 상태를 확인한다: `pm2 monit`
11. PM2가 프로세스 크래시 시 자동 재시작하는 것을 확인한다

> 💬 **대표**: "프로세스 상태 알려줘"
> 💬 **Main**: "PM2 프로세스 현황입니다:
> | 프로세스 | 상태 | CPU | 메모리 | 재시작 횟수 |
> |---|---|---|---|---|
> | backend | online | 12% | 180MB | 0 |
> | litellm | online | 5% | 95MB | 0 |
> 
> 모두 정상 운영 중입니다."

### 기대결과
- 시스템이 안정적으로 배포되고, 부팅 시 자동 시작된다
- PM2가 프로세스 크래시 시 자동 재시작을 관리한다
- Main에게 물어보면 프로세스 상태를 바로 확인할 수 있다

### 대표 경험
- setup.sh 하나로 환경이 구성되어 **복잡한 설치 과정 없이** 시작 가능
- 시스템이 꺼져도 자동으로 다시 켜지는 **무중단 운영**의 안심
- PM2 터미널 명령어를 몰라도 Main에게 물어보면 되는 편리함

### UI 전환 묘사
- 배포는 CLI(터미널)에서 수행
- 배포 완료 후 웹앱 접속 시: SC-001 온보딩(첫 접속) 또는 SC-010 복구(이전 후)와 동일한 워크스페이스 뷰 표시
- PM2 모니터링은 터미널 전용 (웹앱에서는 Main에게 질문)

### 예외흐름

**E1. 빌드 실패**
> 빌드 오류 로그가 터미널에 표시된다. 의존성 문제, TypeScript 에러 등.
> 💬 **Main**: (접속 불가 - 빌드 실패 시 서버 미시작)

  └─ [14:01] Main -> Part: "할일관리앱 프로젝트 시작"

            ├─ [14:05] Sub -> 기획 인스턴스: "요구사항 분석 후 PRD 작성"
            │    └─ [15:30] 기획 인스턴스 -> Sub: "PRD 완료"
            ├─ [15:35] Sub -> Part: "기획 완료, 승인 요청"
            └─ [16:00] Part -> Main -> 대표: "기획 승인 요청"
                 └─ [16:30] 대표 승인: "반복 일정 추가 후 승인"

**Step 2. 노드 탐색**

4. 대표가 "기획 인스턴스: PRD 완료" 노드를 선택한다
5. 해당 노드의 상세 정보가 사이드 패널에 표시된다:
   - 산출물: PRD.md, 기능목록.md
   - 소요 시간: 1시간 30분
   - 토큰 사용량: 입력 25K / 출력 12K
   - 비용: $0.45
6. "에이전트 상세 보기" 버튼 클릭 -> SC-005의 팝업 모달이 열린다

> 4. [4/15] DB 결정: SQLite 선택
> 5. [4/16] 모델 변경: opus -> sonnet

> 총 5건의 의사결정이 있었습니다."

## SC-023. 이중 저장 및 데이터 정합성

**제목**: Hooks 이벤트 발생 시 노트와 DB에 동시 기록되는 흐름
**전제조건**: 할일관리앱 개발 인스턴스가 작업 중. Hooks가 이벤트를 수집하고 있음.
**사용자 목표**: 데이터가 노트와 DB 양쪽에 정확히 기록되어 각각의 용도로 활용되는 것을 확인한다.
**관련 기능**: [F040, F041, F046]

### 상세 흐름

**Step 1. 이벤트 발생 및 이중 기록**

1. 개발 인스턴스가 코드 구현 작업의 한 단계를 완료한다
2. Claude Code Hooks가 작업 완료 이벤트를 감지한다
3. Hook이 HTTP POST로 백엔드에 이벤트 데이터를 전송한다:
   ```json
   {
     "event": "stage_progress",
     "agent_id": "dev-instance-001",
     "stage": "develop",
     "progress": 80,
     "tokens": { "input": 5200, "output": 3100 },
     "cost": 0.025
   }
   ```
4. 백엔드가 동시에 두 작업을 수행한다:
   - **노트 기록**: .orchestrator/parts/project/subs/todo-app/progress/03-develop.md 업데이트
     - "## 2026-04-16 15:00 — 코드 구현 80% 완료" 추가
   - **DB 기록**: SQLite에 구조화된 레코드 INSERT
     - agent_events 테이블: 이벤트 유형, 시각, 진행률
     - token_usage 테이블: 토큰 수, 비용

**Step 2. 실시간 반영**

5. chokidar가 노트 파일 변경을 감지한다 (파일 시스템 워치)
6. WebSocket으로 웹앱 클라이언트에 변경 데이터를 푸시한다
7. 워크스페이스 뷰 업데이트: 개발 인스턴스 캐릭터 머리 위 말풍선이 "구현 80%" 로 갱신
8. 대시보드 리포트 업데이트: 개발 단계 진행률 바가 60% -> 80%로 자동 업데이트
9. 하단 바 비용 표시가 실시간으로 증가

> 💬 **대표**: "개발 진행률 어때?"
> 💬 **Main**: "할일관리앱 개발 단계가 80% 완료되었습니다. 현재 남은 작업은 반복 일정 기능 구현입니다. 예상 완료 시간은 약 1시간 후입니다."

### 기대결과
- 모든 이벤트가 노트(파일) + DB 양쪽에 일관되게 기록된다
- 노트 = 오케스트레이터의 Source of Truth (에이전트가 읽고 이어서 작업)
- DB = 대시보드/리포트 조회용 (빠른 쿼리)
- 실시간으로 웹앱 UI가 업데이트된다

### 대표 경험
- 진행률이 **실시간으로 알아서 갱신**되어 새로고침할 필요 없음
- Main에게 물어보면 노트를 기반으로 정확한 현황을 보고받을 수 있는 신뢰감
- "데이터가 이중으로 저장되어 하나가 깨져도 안전하다"는 안정감

### UI 전환 묘사
- 실시간 업데이트: 워크스페이스 뷰 캐릭터 말풍선, 대시보드 리포트 진행률 바, 하단 바 비용 — 모두 WebSocket 푸시로 자동 갱신
- 새로고침 없이 UI가 부드럽게 업데이트됨 (숫자 카운트업 애니메이션 등)

### 예외흐름

**E1. DB 기록 실패**
> 노트는 정상 기록되어 에이전트 작업에 영향 없음. DB 기록은 백엔드에서 3회 재시도.
> 💬 **Main**: "DB 동기화에 지연이 발생했습니다. 대시보드 데이터가 일시적으로 최신이 아닐 수 있습니다. 복구 중입니다."
> 재시도 성공 시 DB가 노트 기준으로 갱신됨.

**E2. 노트 기록 실패**
> DB 기록은 성공하여 대시보드 표시는 정상. 노트 기록 실패 오류 로그 생성.
> 💬 **Main**: "노트 파일 기록에 실패했습니다. 디스크 공간이 부족할 수 있습니다. 확인해주세요."
> -> SC-017 디스크 모니터링 연계

**E3. 노트-DB 불일치 감지**
> 시스템이 주기적(5분)으로 노트와 DB를 대조. 불일치 발견 시 노트를 기준으로 DB를 자동 갱신 (노트 = Source of Truth).
> 💬 **Main**: "노트와 DB 사이에 불일치가 발견되어 자동 동기화했습니다. 노트 기준으로 DB를 갱신했습니다."

## SC-024. 알림 트리거 종합

**제목**: 다양한 알림 트리거가 동작하는 종합 시나리오
**전제조건**: 시스템이 운영 중. 알림 설정이 활성화되어 있고, 브라우저 푸시 알림 권한이 허용됨.
**사용자 목표**: 모든 유형의 알림을 적시에 수신하고 처리한다.
**관련 기능**: [F028, F029, F030, F031, F043]

### 상세 흐름

**Step 1. 다양한 알림 트리거 동작**

하루 동안 발생하는 알림들을 시간순으로 나열:

1. **[09:00] 단계 완료 알림**
   - 트리거: 기획 단계 완료
   - 워크스페이스 뷰: 기획 인스턴스 캐릭터 기쁨 점프 모션
   - 푸시: "비서실장: 기획 단계가 완료되었습니다"
   - 대시보드 배지: 알림 +1 (초록 = 완료)

2. **[09:05] 승인 요청 알림**
   - 트리거: 기획 완료 후 대표 승인 필요
   - 워크스페이스 뷰: Main 캐릭터가 내 캐릭터에게 다가와 접촉하는 모션
   - 푸시: "비서실장: 프로젝트부에서 결재가 올라왔습니다"
   - 대시보드 배지: 알림 +1 (노란 = 승인 대기)

3. **[14:30] 오류 + 재시도 실패 알림**
   - 트리거: 인스턴스 3회 재시도 모두 실패
   - 워크스페이스 뷰: 인스턴스 캐릭터 빨간 X + 정지 모션
   - 푸시: "비서실장: 프로젝트부에서 문제가 발생했습니다. 확인 부탁드립니다"
   - 대시보드 배지: 알림 +1 (빨간 = 오류)

4. **[16:00] 비용 임계값 알림**
   - 트리거: 월 비용이 설정 한도의 80% 도달
   - 하단 바: 비용 표시가 노란색으로 변경
   - 푸시: "비서실장: 이번 달 API 비용이 설정 한도의 80%에 도달했습니다"
   - 대시보드 배지: 알림 +1 (노란 = 경고)

5. **[20:00] 복구 완료 알림** (서버 재시작이 있었을 경우)
   - 트리거: 서버 재시작 후 자동 복구 완료
   - 워크스페이스 뷰: 조명 켜짐 + 캐릭터 복귀 애니메이션
   - 푸시: "비서실장: 서버가 재시작되어 복구가 완료되었습니다"
   - 대시보드 배지: 알림 +1 (파란 = 정보)

**Step 2. 알림 관리**

6. 대시보드 상단에 알림 벨 아이콘: 빨간 뱃지 "5"
7. 대표가 알림 아이콘을 클릭한다
8. 알림 드롭다운 패널이 열린다:
   - 미읽음 알림이 상단에 볼드체로, 읽음은 일반체로 표시
   - 알림 유형별 색상 구분: 초록(완료), 노랑(승인/경고), 빨강(오류), 파랑(정보)
9. 대표가 특정 알림을 선택하면 해당 상세 화면으로 이동한다:
   - 승인 알림 -> 승인 팝업 (승인 요청 메시지)
   - 오류 알림 -> 팝업 모달 (해당 인스턴스 로그)
   - 비용 알림 -> 대시보드 (비용 섹션)

> 💬 **대표**: "오늘 알림 정리해줘"
> 💬 **Main**: "오늘 알림 요약입니다:
> - 단계 완료: 1건 (기획)
> - 승인 요청: 1건 (처리 완료)
> - 오류: 1건 (수동 복구 완료)
> - 비용 경고: 1건 (한도 80% 도달)
> - 복구: 1건 (서버 재시작)
> 
> 현재 미처리 건은 없습니다."

### 기대결과
- 모든 트리거 유형에 대해 적시에 알림이 발송된다
- 알림 메시지가 비서실장 말투로 통일된다
- 알림별 색상/아이콘으로 유형을 즉시 구분할 수 있다
- 알림 클릭 시 해당 상세 화면으로 바로 이동한다

### 대표 경험
- 다양한 유형의 알림이 **일관된 비서실장 말투**로 전달되어 자연스러움
- 색상과 아이콘으로 **긴급도를 즉시 파악**할 수 있는 직관성
- 알림 클릭 한 번으로 상세 화면으로 이동하여 **빠른 대응** 가능

### UI 전환 묘사
- **알림 드롭다운**: 벨 아이콘 클릭 -> 드롭다운 패널 슬라이드다운 (0.2초)
- **알림 -> 상세 화면**: 알림 클릭 시 해당 뷰로 자동 전환
- 알림 색상: 초록(완료), 노랑(승인/경고), 빨강(오류), 파랑(정보)
- 모바일: 알림 목록이 전체 화면 리스트로 표시. 탭 시 채팅 화면 또는 간소 상태 카드로 이동

### 예외흐름

**E1. 브라우저 알림 권한 미허용**

## SC-025. Part 탭 네비게이션 및 뷰 전환

**제목**: Part 탭과 다양한 뷰(워크스페이스/대시보드/설정/리소스 관리) 간 전환하는 흐름
**전제조건**: 프로젝트관리부 + 재무관리부 2개 Part가 생성되어 운영 중.
**사용자 목표**: 다양한 뷰를 자유롭게 전환하며 필요한 정보를 확인한다.
**관련 기능**: [F013, F018]

### 상세 흐름

**Step 1. 뷰 전환 (메인 네비게이션)**

1. 대표가 워크스페이스 뷰(기본)에서 전체 조직을 한눈에 확인한다
   - 프로젝트관리부 공간 + 재무관리부 공간이 나란히 표시
   - 각 부서 캐릭터들의 활동 상태가 보임

2. 상단 메뉴에서 "대시보드" 탭을 탭한다
   - UI 전환: 워크스페이스 뷰가 페이드아웃, 대시보드가 페이드인
   - 프로젝트 진행 보고서, 의사결정 이력, 리포트 등 종합 현황

3. 상단 메뉴에서 "설정" 탭을 탭한다
   - UI 전환: 대시보드가 페이드아웃, 설정 화면이 페이드인
   - 조직 설정, 승인 정책, 알림 설정 등

4. 상단 메뉴에서 "리소스 관리" 탭을 탭한다
   - UI 전환: 설정 화면이 페이드아웃, 리소스 관리 뷰가 페이드인
   - 비용 차트, 로그 테이블, 감사 로그

**Step 2. Part 탭 네비게이션**

5. 상단에 Part 탭이 표시된다: [전체] [프로젝트관리부] [재무관리부]
6. "프로젝트관리부" 탭을 클릭한다
   - 워크스페이스 뷰: 프로젝트관리부 공간이 확대되어 표시 (줌인)
   - 대시보드: 프로젝트관리부의 리포트만 필터링
   - 리소스 관리: 프로젝트관리부의 비용/로그만 필터링
7. "재무관리부" 탭을 클릭한다
   - 동일하게 재무관리부 중심으로 전환
8. "전체" 탭을 선택하면 모든 Part의 통합 뷰로 복귀

> 💬 **대표**: "재무관리부 현황 보여줘"
> 💬 **Main**: "재무관리부 현황입니다:
> - 진행 중인 작업: 월간 지출 분석 (80%)
> - 에이전트: 분석 인스턴스 1개 활동 중
> - 이번 달 비용: $12.30
> 
> 상세는 재무관리부 탭에서 확인하실 수 있습니다."

**Step 3. 새 Part 추가 시 탭 자동 확장**

9. (가정) SC-018에서 일상관리부를 새로 생성한다
10. 상단 Part 탭에 [일상관리부] 탭이 자동으로 추가된다
11. 워크스페이스 뷰에 새 부서 공간이 나타난다

### 기대결과
- 워크스페이스/대시보드/설정/리소스 관리 뷰를 자유롭게 전환할 수 있다
- Part 탭으로 부서별 정보에 빠르게 접근할 수 있다
- 새 Part 추가 시 UI가 자동으로 확장된다

### 대표 경험
- **한 곳에서 모든 정보**에 접근할 수 있는 통합 인터페이스
- Part 탭으로 부서별로 빠르게 전환하여 **부서별 현황을 즉시 파악**
- 뷰 전환이 부드럽고 직관적이어서 **복잡한 정보를 쉽게 탐색**

### UI 전환 묘사
- **메인 뷰 전환**: 상단 메뉴 바에 4개 탭 (워크스페이스 | 대시보드 | 설정 | 리소스 관리)
  - 선택된 탭: 파란색 하이라이트 + 밑줄
  - 전환 애니메이션: 슬라이드(좌우) 또는 페이드(상하) 0.3초
- **Part 탭 전환**: 상단 탭 바. 선택된 탭에 밑줄 표시
  - 워크스페이스 뷰: 선택 Part 공간 줌인 / 전체: 줌아웃
  - 다른 뷰: 해당 Part로 필터링
- **데스크톱**: 워크스페이스 뷰 내에서 Main에 접촉하여 채팅 패널 오픈 가능
- **모바일**: 하단 3탭 (채팅 | 알림 | 상태). 워크스페이스/리소스 관리 뷰 없음

### 예외흐름

**E1. Part가 없는 초기 상태**
> Part 탭 영역에 "아직 부서가 없습니다. Main에게 첫 부서 생성을 요청해주세요." 안내 표시.
> -> SC-001 온보딩으로 유도

**E2. Part가 1개만 있을 때**
> [전체] [프로젝트관리부] 탭이 표시된다. 1개뿐이어도 탭 구조 유지 (확장 대비).

## SC-026. AI Gateway 및 모델 라우팅

**제목**: LiteLLM을 경유한 모델 호출과 모델 라우팅이 동작하는 흐름
**전제조건**: LiteLLM 프록시가 localhost:4000에서 실행 중. 프로젝트관리부 Skill에 MODEL_ROUTING: claude-sonnet이 기본 설정됨.
**사용자 목표**: 모든 AI 모델 호출이 LiteLLM을 경유하고, Part별 모델 라우팅이 동작하는 것을 확인한다.
**관련 기능**: [F011, F022, F044, F045, F046]

### 상세 흐름

**Step 1. 인스턴스 생성 시 모델 선택**

1. Sub가 코드 리뷰 단계에 도달하여 리뷰 인스턴스를 생성하려 한다
2. Part Skill의 MODEL_ROUTING 설정과 인스턴스 역할(instance-roles.md)을 참조한다
   - 리뷰 인스턴스 기본 모델: claude-haiku

> 💬 **Main**: "코드 리뷰 인스턴스를 생성합니다. 기본 모델은 claude-haiku입니다. 다른 모델로 변경하시겠습니까?"
> 💬 **대표**: "리뷰는 좀 더 꼼꼼하게 하고 싶어. 다른 모델 추천해줘"
> 💬 **Main**: "코드 리뷰에 적합한 모델 비교입니다:
> | 모델 | 품질 | 속도 | 비용 (1M 토큰) | 적합도 |
> |---|---|---|---|---|
> | claude-opus | 최상 | 보통 | $15.00 | 복잡한 아키텍처 리뷰 |
> | claude-sonnet | 높음 | 빠름 | $3.00 | 일반 코드 리뷰 (권장) |
> | claude-haiku | 보통 | 매우 빠름 | $0.25 | 단순 스타일 체크 |
> 
> 할일관리앱 규모에서는 sonnet을 권장합니다."
> 💬 **대표**: "sonnet으로 해"

**Step 2. LiteLLM 경유 API 호출**

3. 인스턴스가 생성되고, claude-sonnet 모델로 설정된다
4. 워크스페이스 뷰에서 리뷰 인스턴스 캐릭터가 등장 — 팀 구역에 앉아 노트북을 펼침
5. 모든 API 호출이 LiteLLM 프록시(localhost:4000)를 경유한다:
   ```
   인스턴스 -> LiteLLM(localhost:4000) -> Anthropic API -> 응답
   ```
6. LiteLLM이 각 호출의 입력/출력 토큰 수와 비용을 기록한다
7. Hooks가 토큰/비용 데이터를 DB에 저장한다

> 💬 **Main**: "리뷰 인스턴스가 코드 리뷰를 시작했습니다. claude-sonnet 모델을 사용하고 있습니다."

**Step 3. 비용 추적 및 대시보드 반영**

8. 리뷰 진행 중 토큰 사용량과 비용이 실시간으로 대시보드에 반영된다
9. 리뷰 완료 후:

> 💬 **Main**: "코드 리뷰가 완료되었습니다. 리뷰 결과:
> - 리뷰 코멘트: 8건 (보안 2, 성능 3, 스타일 3)
> - 토큰 사용: 입력 45K / 출력 12K
> - 비용: $0.17
> 
> 리뷰 코멘트를 확인하시겠습니까?"

### 기대결과
- 모든 모델 호출이 LiteLLM을 경유한다 (직접 API 호출 없음)
- Part별 MODEL_ROUTING에 따라 적절한 모델이 추천되고, 대표가 최종 선택한다
- 토큰/비용이 정확히 수집되어 대시보드에 즉시 반영된다

### 대표 경험
- Main이 태스크에 맞는 모델을 비교표로 추천해주어 **최적의 선택**이 가능
- 모든 비용이 투명하게 추적되어 **어디에 얼마가 쓰이는지** 명확
- LiteLLM 경유로 **어떤 AI 제공사든** 동일한 방식으로 사용할 수 있는 유연함

### UI 전환 묘사
- 모델 추천: 채팅에서 테이블 형식으로 표시. 별도 UI 전환 없음
- 비용 반영: 하단 바 비용 표시가 실시간 증가 (숫자 카운트업 애니메이션)
- 인스턴스 생성: 워크스페이스 뷰에서 새 캐릭터 등장 애니메이션

### 예외흐름

**E1. LiteLLM 프록시 다운**
> 인스턴스 캐릭터 머리 위 ❗ 표시 + 당황 모션
> 💬 **Main**: "AI Gateway(LiteLLM)에 연결할 수 없습니다. 모든 AI 모델 호출이 일시 중단됩니다. LiteLLM 상태를 확인해주세요."
> 💬 **대표**: "터미널에서 확인해볼게"
> 대표가 터미널에서 `pm2 restart litellm` 실행 -> 복구 후:
> 💬 **Main**: "LiteLLM이 복구되었습니다. 대기 중이던 인스턴스가 작업을 재개합니다."

**E2. 선택 모델의 API 키 만료**
> 💬 **Main**: "claude-sonnet 호출에서 인증 오류가 발생했습니다. Anthropic API 키가 만료되었을 수 있습니다."
> -> SC-011 API 키 관리 흐름으로 연결

**E3. 모델 응답 품질 불만족**

> 💬 **Main**: "모델을 claude-sonnet으로 변경하여 재리뷰를 진행할까요? 추가 비용은 약 $0.15입니다."

## SC-027. 모바일 간소화 뷰

**제목**: 모바일 브라우저에서 간소화된 UI로 시스템을 모니터링하는 흐름
**전제조건**: 시스템이 운영 중. 대표가 모바일 브라우저에서 접속.
**사용자 목표**: 모바일에서 핵심 정보를 빠르게 확인하고, 기본적인 지시/승인을 처리한다.
**관련 기능**: [F013, F028, F029]

### 상세 흐름

**Step 1. 모바일 채팅 화면 (기본)**

1. 대표가 모바일 브라우저에서 ClaudeManager에 접속한다
2. 로그인 후 모바일 채팅 화면이 기본으로 표시된다
   - 아이소메트릭 워크스페이스 뷰는 모바일에서 표시하지 않음 (화면 크기 한계)
   - 상단: Main(비서실장) 아이콘 + 이름 + 연결 상태(초록 점)
   - 중앙: 채팅 메시지 영역
   - 하단: 메시지 입력창 + 네비게이션 바(채팅 | 알림 | 상태)

> 💬 **Main**: "모바일로 접속하셨네요. 현재 현황을 간단히 보고드립니다:
> - 프로젝트관리부: 개발 단계 진행 중 (80%)
> - 재무관리부: 월간 분석 완료
> - 승인 대기: 0건
> - 오류: 0건
> 
> 무엇을 도와드릴까요?"

3. 대표가 채팅으로 지시/질문을 한다

> 💬 **대표**: "개발 완료 예상 시간?"
> 💬 **Main**: "현재 진행률(80%) 기준, 약 2시간 후 개발이 완료될 것으로 예상됩니다. 완료되면 알림을 드리겠습니다."

**Step 2. 알림 목록 탭**

4. 대표가 하단 "알림" 탭을 탭한다
5. 알림 목록이 시간순으로 표시된다:
   - [16:00] 비용 경고 — 한도 80% 도달 (노랑)
   - [15:30] 기획 완료 — 승인 처리됨 (초록, 처리 완료)
   - [14:30] 오류 발생 — 수동 복구됨 (빨강, 처리 완료)
6. 미처리 알림은 볼드체 + 색상 구분, 처리 완료는 회색 처리
7. 알림 탭 시 해당 상세로 이동 (채팅 화면의 관련 메시지로 스크롤)

**Step 3. 간소 상태 카드 탭**

8. 대표가 "상태" 탭을 탭한다
9. Part/Sub별 상태가 카드형으로 요약 표시된다:

```
[프로젝트관리부] 정상
  캐릭터 아이콘 | 할일관리앱: 개발 80% | 에이전트 3개 활동

[재무관리부] 정상
  캐릭터 아이콘 | 월간 분석: 완료 | 에이전트 0개 (대기)
```

10. 카드를 탭하면 해당 Part의 요약 정보가 펼쳐진다 (하위 Sub/인스턴스 상태)
11. "데스크톱에서 자세히 보기" 링크 제공

> 💬 **대표**: "재무관리부 다음 작업은 뭐야?"
> 💬 **Main**: "재무관리부의 다음 예정 작업은 주간 투자 포트폴리오 검토입니다. 내일(월요일) 자동 시작 예정입니다."

### 기대결과
- 모바일에서 채팅 + 알림 + 상태 카드로 핵심 정보에 접근할 수 있다
- 화면 크기에 최적화된 간소화 UI가 제공된다
- Main에게 질문하면 데스크톱 없이도 필요한 정보를 얻을 수 있다

### 대표 경험
- 이동 중에도 **Main과 대화만으로** 조직 현황을 파악하고 지시할 수 있는 유비쿼터스 경험
- 복잡한 UI 없이 **핵심 정보만** 빠르게 확인할 수 있는 간편함
- "데스크톱에서 자세히 보기"로 **필요할 때 상세 확인**이 가능한 유연함

## SC-028. 데이터 민감도 관리

**제목**: Part별 데이터 민감도 수준에 따라 저장 방식이 달라지는 흐름
**전제조건**: SC-018에서 재무관리부가 "극민감"으로 설정됨. 프로젝트관리부는 "일반"으로 설정됨.
**사용자 목표**: 민감한 데이터가 설정된 보호 수준에 따라 안전하게 관리되는 것을 확인한다.
**관련 기능**: [F009, F039, F047, F048]

### 상세 흐름

**Step 1. 민감도 수준별 저장 방식 확인**

> 💬 **대표**: "재무관리부 데이터 보안은 어떻게 되어있어?"
> 💬 **Main**: "재무관리부의 데이터 보안 현황입니다:
> | 항목 | 설정 |
> |---|---|
> | 민감도 수준 | 극민감 |
> | 데이터 암호화 | AES-256-GCM 적용 |
> | 저장 위치 | 로컬 전용 (외부 전송 차단) |
> | API 제한 | 금융 쓰기 API 구조적 차단 |
> | 백업 | 암호화된 상태로 백업 |
> 
> 투자 데이터, 지출 내역 등 모든 재무 데이터가 암호화되어 저장됩니다."
> 💬 **대표**: "프로젝트관리부는?"
> 💬 **Main**: "프로젝트관리부는 민감도 '일반'으로 설정되어 있습니다:
> | 항목 | 설정 |
> |---|---|
> | 민감도 수준 | 일반 |
> | 데이터 암호화 | 미적용 (일반 저장) |
> | 저장 위치 | 로컬 기본 |
> | API 제한 | 없음 |
> 
> 코드, PRD 등 프로젝트 데이터는 일반 방식으로 저장됩니다."

**Step 2. 민감도 수준별 동작 차이**

1. **극민감 (재무관리부)**:
   - 모든 노트(.orchestrator/parts/finance/) 파일이 AES-256-GCM으로 암호화 저장
   - API 키는 별도 암호화 저장소에 보관
   - 외부 네트워크로의 데이터 전송 차단
   - 금융 쓰기 API(결제, 이체) 구조적 차단 — 읽기만 가능
   - 백업 시에도 암호화 상태 유지

2. **민감** (향후 생성 가능):
   - 노트 파일 암호화 저장
   - 로컬 전용 저장 (외부 전송 차단)
   - 금융 쓰기 API 차단

3. **일반 (프로젝트관리부)**:
   - 기본 저장 방식 (암호화 미적용)
   - 별도 제한 없음

**Step 3. 민감도 수준 변경 시나리오**

> 💬 **대표**: "프로젝트관리부도 민감으로 올리고 싶어. 가능해?"
> 💬 **Main**: "민감도 수준을 '일반'에서 '민감'으로 변경할 수 있습니다. 다만:
> - 기존 저장된 데이터를 암호화 처리해야 합니다
> - 데이터 양에 따라 수 분 소요될 수 있습니다
> - 처리 중 해당 Part의 에이전트가 일시 정지됩니다
> 
> 진행할까요?"
> 💬 **대표**: "아니, 일반으로 둘게"
> 💬 **Main**: "현재 설정을 유지하겠습니다."

### 기대결과
- 데이터 민감도 3단계(극민감/민감/일반)가 정확히 적용된다
- 극민감 데이터는 반드시 암호화 저장된다
- 금융 쓰기 API는 민감도와 무관하게 구조적으로 차단된다
- 민감도 수준을 변경할 수 있으나, 기존 데이터 처리에 대한 사전 안내가 제공된다

### 대표 경험
- 재무 데이터가 **자동으로 암호화**되어 저장되는 것에서 **금융 보안** 에 대한 안심
- Main에게 물어보면 현재 보안 설정을 표로 정리해주어 **투명하게 파악**
- 금융 쓰기 API가 구조적으로 차단되어 **실수로 금융 거래가 일어나지 않는다** 는 안전감

### UI 전환 묘사
- 민감도 관련 설정: 설정 화면 -> Part별 정책 -> 민감도 수준 선택
- 극민감 Part: 워크스페이스 뷰에서 해당 부서 공간에 자물쇠 아이콘 표시
- 민감도 변경: 확인 모달 + 프로그레스 바 (암호화/복호화 처리)

| **마크다운 형식** | Obsidian에서 읽을 수 있는 표준 마크다운 |
| **이중 저장** | 노트(파일) + DB 동시 기록 |
| **노트 = Source of Truth** | 오케스트레이터는 노트를 읽고 작업, DB는 대시보드 조회용 |

### 기대결과
- 모든 에이전트의 작업 내용이 구조화된 노트로 자동 기록된다
- 대표가 웹앱에서 노트를 실시간으로 열람할 수 있다
- 서버 재시작 시 노트를 기반으로 완전 복구가 가능하다
- Obsidian에서도 직접 노트를 열어 확인할 수 있다

### 대표 경험
- 에이전트들이 알아서 문서를 정리하는 모습에서 **"진짜 조직처럼 인수인계 문서를 남기는구나"** 라는 신뢰감을 느낀다
- 진행 상황을 Main에게 물어보면 노트를 기반으로 즉시 정리해서 보고해주는 편리함
- 서버가 꺼져도 노트가 살아있어 **"작업이 날아갈 걱정이 없다"** 는 안정감

### 예외흐름

**E1. 노트 파일 손상/누락**
> 💬 **Main**: "할일관리앱 프로젝트의 sub-context.md가 손상되었습니다. 최근 백업에서 복구할까요?"

**E2. 노트와 DB 불일치**
> 시스템이 주기적으로 노트와 DB를 대조하여 불일치 발견 시 노트를 기준으로 DB를 갱신한다 (노트 = Source of Truth)

**E3. 디스크 용량 부족**
> 💬 **Main**: "디스크 사용량이 90%에 도달했습니다. 완료된 프로젝트의 노트를 아카이브할까요?"
